# Project Scaffolding Spec

This document defines the **canonical scaffold** every project instantiates at kickoff. The goal: an AI-assisted development loop that runs on **structured data and a fixed file contract**, so skills pick up predictably without re-reading the whole repo, and the progress dashboard renders from data instead of LLM reasoning.

## Ownership legend

Every file below is owned by exactly one writer. Mixed ownership is what causes drift.

| Tag | Owner | Meaning |
|-----|-------|---------|
| 👤 **human** | You | Hand-authored or approved; skills never overwrite. |
| 🤖 **skill** | define/implement/ship skills | Generated/updated by the workflow skills. |
| ⚙️ **script** | Node scripts | Generated mechanically; never hand-edited. |
| 📐 **template** | Bootstrap | Copied once at init, then filled. |

## File-by-file purpose

### Root

**`AGENTS.md`** 🤖/👤 — The agent's operating manual and the most important file in the scaffold. Human docs are for humans; this is the machine-facing index every skill/session reads first. It states: where the contract lives (`docs/engineering/backlog.json`), the status enum and who owns it, the define→implement→ship workflow, the approval gates, and the exact commands to refresh the dashboard. This is what lets skills orient in ~200 tokens instead of re-parsing the repo. Generated by bootstrap, refined by hand.

**`PROGRESS_DASHBOARD.html`** ⚙️ — Generated artifact. Never edited directly; produced by `build-dashboard.mjs`.

### `docs/product/` — PM tier 👤

Standard product set. The only structurally load-bearing file is **`06-prd.md`**: each requirement carries a stable ID (`REQ-01`, `REQ-02`…) so backlog stories can reference a *requirement*, not a fuzzy heading. This is what makes "is requirement X built and tested?" answerable by script.

### `docs/architecture/` — Arch tier 👤

System overview, data model, API, infra. **`decisions/`** holds ADRs (one file per decision) generated via the architecture skill and linked back to the story that triggered them — so design reasoning accumulates instead of evaporating.

### `docs/design/` — Design tier 👤

Design system: tokens, component primitives, UI kit. Unchanged from current structure.

### `docs/engineering/` — the handoff layer

**`backlog.json`** 🤖/👤 — **THE CONTRACT.** The single source of truth for what work exists, its order, dependencies, and state. Everything downstream (skills, sync, dashboard) derives from this. Field ownership is partitioned to avoid clobbering: human + define-skill own `scope/order/deps/epic/gh_issue`; `sync-status.mjs` owns `status` and `blocked_by` only and never touches scope. Per-story shape:

```json
{
  "id": "S-08",
  "title": "Manual Add",
  "phase": "D1",
  "prd_ref": "REQ-12",
  "epic": 50,
  "gh_issue": 48,
  "status": "in_progress",
  "blocked_by": [],
  "order": 8,
  "acceptance": "…",
  "verify": { "ci": "pass", "coverage": 0.0 }
}
```

Status enum (the only legal values): `notstarted | in_progress | blocked | done`.

**`backlog.schema.json`** 📐 — JSON Schema for the contract. A contract without a validator isn't a contract; this is what `validate.mjs` enforces so one malformed write can't silently break the dashboard.

**`01-tech-plan.md`** 👤 — How the build is sequenced: phases (D1/D2/D3…), milestones, gate dates. The narrative layer above the backlog.

**`workflow.md`** 📐 — The encoded gates the skills check: **Definition of Ready** (when a story may be picked up — e.g. PRD `status: approved`, acceptance criteria present), **Definition of Done** (tests pass + committed + ledger updated), and the **human approval checkpoints** (PRD approved before backlog seeding; epic plan reviewed before implementation).

### `docs/_templates/` 📐

Empty stubs — front-matter block + required section headings — for every doc type. "Industry-standard docs" means *these headings are guaranteed present every time*; generation only fills content. Bootstrap copies these into place (deterministic, zero tokens) before any LLM fill step.

### `scripts/`

**`init-project.mjs`** ⚙️ — Phase A bootstrap. Creates the tree, copies `_templates/` into place, writes an empty `backlog.json` (`{ "schema": 1, "prd": "docs/product/06-prd.md", "stories": [] }`). Deterministic; no LLM.

**`validate.mjs`** ⚙️ — Validates `backlog.json` against the schema. Runs in a pre-commit hook and at the top of the dashboard build. Fails loud.

**`sync-status.mjs`** ⚙️ — Reads `.throughline/ship-*/issue-*.json` (or the GH API) and stamps `status` / `blocked_by` into `backlog.json`. The only writer of those fields. No LLM in this path.

**`build-dashboard.mjs`** ⚙️ — Pure function: `backlog.json` + computed summary → `PROGRESS_DASHBOARD.html`. Zero dependencies. Renders both the current-release work board (progress) and a Planning section (gate pipeline strip from `.throughline/gates.json`, plus a phase-grouped roadmap across all releases).

**`dashboard.template.html`** 📐 — The view; data is injected at build time.

### `.throughline/` 🤖

Skill working state — untouched by hand. `epic-<n>/` holds `epic.json`, `sub-<n>.json`, and `ledger.md` (commits, tests, status, risks). `ship-<n>/issue-<n>.json` carries the live GH issue number + state. `sync-status.mjs` reads from here to update the contract.

## The data flow (why this stays predictable)

```
PRD (REQ-ids, approved) ─┐
                         ▼
              backlog.json  ◄── human seeds stories (id, order, deps, prd_ref)
                 │  contract
                 ▼
        define-epic  →  reads next unblocked story, creates GH epic/issue,
                        writes epic + gh_issue back into backlog.json
                 │
                 ▼
        implement / ship  →  update .claude ledgers + GH issue state
                 │
                 ▼
        sync-status.mjs  →  mirrors GH state into backlog.json (status only)
                 │
                 ▼
        validate.mjs → build-dashboard.mjs  →  PROGRESS_DASHBOARD.html
```

The LLM only reasons at the **define** step. Everything downstream is data through scripts — deterministic, cheap, drift-free.

## Bootstrap, two phases

- **Phase A — scaffold (deterministic):** `init-project.mjs` builds the tree, copies templates, seeds empty contract + `AGENTS.md`. Structure can never come out different because it's copied, not generated.
- **Phase B — fill (LLM):** generators write into the stubs (PRD via write-spec, architecture, design). Then a "seed backlog" step turns approved PRD requirements into `stories[]`. After that, call `define-epic`.

## Notes / open decisions

- **Hierarchy depth:** for a solo dev, collapse *slice* and *epic* into one level (one story = one epic). Add the extra layer only when collaborators need it. Match ceremony to team size.
- **define-* read path:** the skills must be pointed at `docs/engineering/backlog.json` as their pickup source and taught to write `epic`/`gh_issue` back. This is the one skill change required for automatic pickup.
- This file lives in `docs/_temp/` as a working spec. Once approved, promote the durable parts into `docs/engineering/workflow.md` + `AGENTS.md` and delete `_temp/`.
